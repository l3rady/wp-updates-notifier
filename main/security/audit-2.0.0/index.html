    Security audit for 2.0.0¶

    The security sign-off for 2.0.0 (#228, the last step of the security epic #229). It records a result for every item of three checklists, run against main at d2f4377 on 2026-10-26:

    • OWASP ASVS 5.0.0 Level 1: all 70 requirements.
    • The OWASP Top 10:2025, mapped onto the ASVS results.
    • The security chapter of the WordPress developer handbooks, and the WordPress.org plugin guidelines that bear on security and trust.

    It also re-checks the areas #228 names, and every suppression of a security sniff or rule.

    Result: no High or Medium finding is open for 2.0.0, and nothing blocks the release once #328 is merged.

    • On a single site, the only setup 2.0.0 supports, there are no findings above Info.
    • Multisite: three Medium findings, fixed in #328.
    • They share one cause: the default capability let a site administrator who is not a super admin use the settings.
    • On multisite that person could:
      • mail out the network's list of pending updates, which core shows only to super admins;
      • pick up channel settings that a network owner set in wp-config.php for another site;
      • send mail through the network's mailer from any From address.
    • The threat model counted that site administrator as trusted, so these sit on the old trust boundary rather than below it. #328 moves the boundary to match core: on multisite only super admins manage the plugin by default.
    • Low and Info hardening: 16 items, none reachable from below the trust boundary. They are filed as #329 (plugin code) and #330 (CI and release), for 3.0.0.
    • Fixed in the audit branch: one documentation gap (V15.1.1). SECURITY.md now gives fix times for vulnerable development tools.
    • Reporting channel: the reporting policy in SECURITY.md now promises a reply within 7 days and a fix or a plan within 30 days. No third-party disclosure programme was joined (decision on #228): GitHub private vulnerability reporting stays the one channel.

    Method¶

    The audit is checklist-driven, so it can be repeated for a later release.

    • Scope: includes/, modules/, uninstall.php, wp-updates-notifier.php, bin/, .github/, the release build, and the GitHub repository settings that the release depends on.
    • Who did it: the maintainer's session split the checklists into three slices: encoding and validation; authorisation, data and configuration; secure coding and supply chain. Each slice was a read-only source review with the WordPress Security Skills pack, checked against the WordPress 7.1.3 source. The maintainer's session then verified every Fail and every open question itself, and decided the N/A rows.
    • Severity rubric:
    Severity What it means
    Critical Unauthenticated code execution, SQL injection or authentication bypass.
    High Reachable by a visitor or a low-privilege user: stored XSS, CSRF on a state change, privilege escalation, or a secret disclosed to someone who isn't an administrator.
    Medium Needs an unusual setup, or a lower-trust user with limited impact.
    Low or Info Hardening, or input the threat model trusts. That input is administrators, add-on code, translations, api.wordpress.org data, and wp-config.php or the environment.
    • Inputs:
    • the threat model;
    • the triaged AI review (#230), whose five hardening items were fixed in #325 before this audit;
    • the security test group;
    • the scripted tools below.

    Repository settings¶

    Checked with gh api on 2026-10-26.

    • release environment: deploys only from protected branches and needs the maintainer's approval. It holds RELEASE_SIGNING_KEY.
    • wordpress-org environment: deploys only v* tags and needs the maintainer's approval. It holds the SVN username and password.
    • Repository-level secrets: RELEASE_APP_PRIVATE_KEY is the only one. Moving it into an environment is CI4 in #330.
    • release tags ruleset: active on refs/tags/v*. It blocks deletion, updates and non-fast-forward moves, and has no bypass actors.
    • main branch protection: requires signed commits, linear history and the required checks.

    V16 Security Logging and Error Handling¶

    ASVS 5.0 has no Level 1 requirement in this chapter. #228 asks for a note on it all the same:

    • Debug log: when WP_DEBUG is on, a module that throws is logged with its instance id, type and exception class. The message and stack trace are never logged, because a message can hold a webhook URL.
    • Delivery results: they keep a fixed message, plus the exception class.
    • _doing_it_wrong notices: they name types and fields, never values.
    • Site Health: it lists rejected configuration keys with their source, never the value.
    • last_result: it is shown only to administrators, escaped.

    The proof is security/test-secrets.php::test_a_secret_never_shows. It covers delivery results, stored state, notices, every tab, Site Health, print_r and var_dump, configuration problems, _doing_it_wrong messages and the PHP error log.

    Two gaps are filed in #329:

    • HN6: a failed send stores the mailer's error text as it is.
    • HN8: a module that throws outside its send() stops the whole check, which is narrower than threat model §6 promises.

    Outbound messages¶

    1. The notification email, to the recipients an administrator configured. It is sent:
    2. by the cron event, at the chosen frequency;
    3. by "Check now" and "Send test", each behind the capability and a security token;
    4. by sc_wpun_run_check, from trusted code.
    5. A one-time email about the Slack channel being removed. It goes to the email channel's recipients, or to the admin email if there are none.
    6. The deprecated send_email_message(), only when trusted code calls it.
    7. Core's own update checks to api.wordpress.org, which the plugin fires before each check. Core rate-limits them itself.

    Email header injection¶

    Value Control
    From address sanitize_email and is_email on save, sanitize_email again at send, then core's validator in setFrom.
    From name A translation, which is trusted. PHPMailer's setFrom strips CR and LF and encodes the header.
    Reply-To sanitize_email, then core's addReplyTo validation.
    Subject and prefix The prefix uses sanitize_text_field. On every path PHPMailer's secureHeader strips CR and LF from the subject, including subjects from filters and channels defined in code.
    Recipients sanitize_email for each address. Payload addresses that contain CR or LF are dropped. PHPMailer validates each one.
    Extra headers Lines with CR or LF are dropped, and core's addCustomHeader refuses them too.

    Proof: security/test-settings-input.php::test_a_line_break_in_the_email_settings_adds_no_header and test-email-channel.php::test_the_payload_filter_may_only_return_safe_values.

    Findings¶

    Medium (multisite, fixed in #328)¶

    On multisite, the default capability manage_options let a site administrator who is not a super admin use the settings. That gave them three things core does not:

    • M1: a list of the network's pending core, plugin and theme updates, with installed versions, mailed to any address. Core shows that list only to super admins.
    • M2: channel settings set in wp-config.php for another site. Constants apply on every site, so a channel created with the same id picks them up.
    • M3: mail sent through the network's mailer from any From address.

    2.0.0 doesn't support multisite (ADR 0008), and the threat model trusted site administrators. #328 changes the default capability on multisite to manage_network_options. Networks that want site administrators to manage the plugin can grant it back with the sc_wpun_capability filter.

    Limits¶

    • This is a source review, backed by the scripted tools and the tests. No manual penetration test was done, apart from the ZAP scan.
    • Core and the host are trusted. Weaknesses in core's own URL checks, such as DNS rebinding, are out of scope.
    • Third-party Actions are taken as pinned. Their internals were not reviewed.
    • The rows are tied to d2f4377. A later release repeats this audit on its diff, using the same checklists, the threat model and the rubric above.
